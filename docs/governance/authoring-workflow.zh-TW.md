# 文件生成與維護流程

[English](authoring-workflow.en.md)

本文件整理已討論的協作規則，作為人員與 skill 共用的流程定義。文件狀態為 Draft，待使用者審閱整理後的內容。公司沒有既有強制模板或審核制度，目前由 Requester 單獨做最終審閱與決策。

## 文件責任

| 類型 | 主要責任 |
| --- | --- |
| 整體 PRD | 問題、使用者、目標、範圍、非目標、成功條件與需求。 |
| Feature Spec | 詳細行為、規則、狀態、例外與驗收條件。 |
| RFC | 待決議題、方案、取捨、建議與最終決策。 |
| System Architecture | 元件、介面、相依關係與責任邊界。 |
| Data Flow | 來源、目的地、轉換、傳遞、失敗與復原行為。 |
| 對外 Service Spec | 使用者可見能力、支援範圍、配額、限制與已核准承諾。 |
| 對外流程、手冊與政策 | 申請、審核、操作、排查，以及使用者責任和使用規範。 |

每項共用事實須有主要定義文件，其他文件以連結引用。草稿不能默默覆蓋已核准決策。有衝突時指出雙方主張及狀態，由使用者裁定產品決策；技術事實依[參考資料規範](reference-policy.zh-TW.md)調查。

## 內容狀態與文件生命週期

| 內容狀態 | 意義 |
| --- | --- |
| 已確認現況 | 有實作、設定、觀察、測試或使用者對實際運作的明確確認，須指出依據。 |
| 已決議規格 | 已決定，但可能尚未完成實作或開放。 |
| 提案 | 等待決策的建議，須交代理由。 |
| 假設 | 暫用且待驗證的前提。 |
| 待釐清問題 | 缺少資訊或尚未決定，須說明影響。 |

文件生命週期為 `Draft → In Review → Approved → Published`；僅在適用時使用 Published，被替代文件使用 `Superseded`。文件核准不代表功能已上線。不得自行標示人工核准、實作驗證或發布。

既有 Pipeline 設計依使用者授權視為文件現況基準，但不代表已驗證正式環境運作。其機密文件不匯入；相依資訊按需詢問，未回答時保留待釐清。

## 混合式工作流程

1. 閱讀 repository 指引、相關文件與使用者決策，確認讀者、類型、範圍與相依關係，保留既有修改。
2. 先釐清會影響服務承諾、架構、存取邊界、資料語意或驗收條件的重要問題；相關問題集中詢問。
3. 其餘先寫草稿，標示提案、假設與待釐清事項，不虛構 SLA／SLO、配額、保留期限、介面、支援時間或交付日期。數值範例須與正式需求區分。
4. 核對重要主張及來源，區分 Apache Doris 上游能力、本服務範圍與實際可用狀態。
5. 產出中英文配對並核對語意。新主題先定義目的與邊界，再細化設計；沿用已確認骨架，不自行擴增文件類型。
6. 向使用者摘要變更、待決問題、證據缺口與受影響文件，由使用者審閱並決策。
7. 依使用者指示定稿／發布，同步相關文件與語言版本。重要決策記錄 ID、內容、審閱者、已知日期與理由／來源，不虛構歷史資訊。

## Metadata 與雙語維護

每份文件使用 YAML frontmatter：`doc_id`、`document_type`、`audience`、`status`、`revision`、`reviewer`、`applies_to`、`language`，並在正文提供另一語言的相對連結。已知時才增加 owner 或日期。Metadata 欄位名稱及共享值採一致的英文識別方式；`TBD` 表示尚未決定。

- 同主題檔案位於同一目錄，使用 `.zh-TW.md`／`.en.md`，共用 ID、revision、狀態及適用範圍。
- 兩種語言具有相同語意地位；先以討論語言起草，再產出另一版。歧義交由使用者確認。
- 需求、數值、單位、範例、限制、證據狀態、引用、待釐清問題及 `must`／`should`／`may` 的強度須一致。
- 中文使用繁體中文並保留英文技術術語，縮寫首次出現時說明，名稱依[術語表](glossary.zh-TW.md)。
- 兩版未同步時回報未完成，不送核准。保留既有結構，不自行大量重新命名或翻譯無關文件。
- skill 是命名例外：`SKILL.md` 為入口，`SKILL.zh-TW.md` 為中文對照。

## 對外草稿與正式內容

目前對外文件是撰寫骨架；其中待釐清問題是作者工作項目，不是使用者操作指示，也不代表服務承諾。正式發布前須解決相關缺口。

- 對外正式內容須符合目標使用者已確認可用的能力及已核准承諾。應要求才提前描述規劃／preview，並明確標示狀態。
- Service Spec 定義能力與技術限制；Usage Policy 定義使用者責任。使用手冊引用規格，不另定配額或承諾。
- 不推定申請審核者、時限或核准保證；本文件的 Requester 是文件審閱者，不自動是服務申請審核者。
- Monitoring／logs 的權限與遮蔽政策在內部規格決定；對外範例、截圖、圖表及 logs 須遵循已決定規則。未決時僅使用明確標示的示意 placeholder，不暴露內部資料。
- 內部基礎設施與程序留在內部文件，除非已核准且使用者需要。外部資料不能決定揭露政策。
- 區分 monitoring、logs、metrics 與 alerting 責任；未來使用者自行告警不表示服務代管告警。

## 完成檢查

- 保留使用者工作，確認讀者、文件類型與內容狀態可辨識。
- 核對重要來源的可信度、適用性與真實驗證狀態。
- 檢查雙語 metadata、ID、數值、規範強度、章節語意與相互連結。
- 共用事實更新時檢查 PRD、Feature Spec、架構／Data Flow、Service Spec 及手冊；更新任務範圍內的相依文件，或列明待同步項目。
- 使用適合文件的工具檢查 Markdown、相對連結與雙語配對。
- 回報異動、決策、待釐清事項及實際驗證／審閱狀態。

## 待釐清事項
