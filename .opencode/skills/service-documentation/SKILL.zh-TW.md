# 服務文件撰寫規範

本文件是 [SKILL.md](SKILL.md) 的繁體中文對照版本；OpenCode 以 `SKILL.md` 為 skill 執行入口。修改規範時須同步兩個版本。產品文件須提供繁體中文與英文版本。

## 1. 目的與讀者

本 repository 用於撰寫公司內部提供的 Apache Doris OLAP Service 與 Data Ingestion Pipeline 文件。

- **對外**指公司其他部門的服務使用者，不代表公開網際網路。
- **內部**指負責設計、實作與維運服務的團隊。
- 公司目前沒有必須遵循的模板或審核制度，採用下述輕量流程。
- 目前由提出需求的使用者單獨負責最終審閱與決策，不自行增加其他審核角色。

| 文件 | 責任 |
| --- | --- |
| PRD | 問題、使用者、目標、範圍、非目標、成功條件與需求。 |
| Feature Spec | 詳細行為、規則、狀態、例外與驗收條件。 |
| RFC | 待決議題、方案、取捨、建議與最終決策。 |
| System Architecture | 元件、介面、相依關係與責任邊界。 |
| Data Flow | 來源、目的地、轉換，以及相關的傳遞、失敗與復原行為。 |
| 對外 Service Spec | 使用者可見的能力、支援範圍、配額、限制與已核准服務承諾。 |
| 對外流程與手冊 | 服務申請、審核、啟用、操作、問題排查與使用規範。 |

依上述責任決定資訊歸屬，以連結引用主要定義文件，避免大量複製。草稿不能直接覆蓋已核准文件的決策；有衝突時應提出供使用者確認。

## 2. 已確認的專案基準

以下是使用者提供的背景，不代表已獨立驗證部署現況。使用者做出新決策時應更新。

- 既有 Data Ingestion Pipeline 文件為已核准設計，實作接近完成。使用者同意將其視為目前的文件現況基準。沒有衝突或新需求時，不反覆重啟已決議設計；但這項授權不代表每項能力都已部署、通過測試或正式開放。
- 既有 Pipeline 文件屬於公司內網機密，目前無法放入本 repository。Pipeline 文件暫留空白，匯入既有文件不是推進其他工作的前提。不要求提供機密原始文件，不虛構其內容，也不宣稱已檢閱。
- 其他文件或 feature 若依賴 Pipeline 行為，僅就必要細節（例如介面、傳遞語意或錯誤處理）向使用者提出具體問題，並說明會影響哪項決策。採用使用者確認適合寫入本 repository 的資訊，來源標示為使用者確認，而非已檢閱無法取得的文件。回答前將相依細節列為待釐清問題，並繼續不受影響的工作。
- Apache Doris 候選版本為 **4.1.0 或 4.1.4**，尚未選定。這是使用者提出的候選，不代表已驗證版本發布狀態或相容性。
- 部署設計是在 **bare-metal 機器上自建 HashiCorp Nomad cluster，搭配 Consul 與 Vault**。Doris FE、BE 以 Docker container 形式，執行於 Nomad agent 上的 Docker daemon。不得由此推定 Consul／Vault 的具體整合、拓樸、儲存、容量或 HA 行為。
- 產品範圍包含提供內部團隊與外部使用者的 **monitoring 與 logs**。外部用途主要是調查與問題排查，並會遮蔽或不提供部分資訊；具體可見範圍與遮蔽規則仍待決定。
- 開放 **metrics** 讓使用者串接並自行實作 alert，是未來可能方向，不是已承諾交付或已可用功能。不得推定協定、endpoint、時程，或服務代管 alerting 的能力。

保留 Doris 版本、monitoring／logging 權限與遮蔽模型等未決事項。當正在撰寫的內容依賴這些決策時再釐清，不阻擋無關工作。

## 3. 證據與決策狀態

當狀態差異會影響解讀時，應明確區分。優先以章節標示或簡短表格呈現，不必逐句加標籤。

| 狀態 | 意義 |
| --- | --- |
| 已確認現況 | 有實作、設定、觀察、測試，或使用者對實際運作的明確確認；須指出依據。 |
| 已決議規格 | 已做出決定，但可能尚未完成實作或上線。 |
| 提案 | 等待決策的建議方案。 |
| 假設 | 暫時採用、仍待驗證的前提。 |
| 待釐清問題 | 缺少資訊或尚未做出決定。 |

文件生命週期與實作狀態分開管理：已核准設計不自動代表服務已可用。依前述約定使用 Pipeline 現況基準，但不將它提升為已驗證的正式環境運作狀態。

- 不得虛構 SLA／SLO、配額、保留期限、限制、API 行為、支援時間、架構選擇或交付日期。
- 可以提出有理由的建議，但須標為提案。數值範例與 placeholder 須和正式需求區分。
- 重要決策記錄識別碼、決策內容、審閱者、已知日期，以及理由或來源。不虛構歷史日期或核准紀錄。
- 輸入衝突時，指出衝突主張及各自狀態。服務或設計決策交由使用者裁定；技術行為則以適用證據調查。

## 4. 外部參考資料 credibility tier

依支持重要主張的具體證據分級，不只依網站或組織名稱分級。

| Tier | 範例 | 可採用方式 |
| --- | --- | --- |
| T1 — 權威第一手證據 | 適用版本的官方文件、release notes、原始碼、正式標準。 | 可作為技術行為與限制的主要依據，但須符合版本、設定與證據涵蓋範圍。 |
| T2 — 可追溯的一手說明 | 維護者 issue／PR 討論、設計提案、交代環境與方法的工程報告。 | 支持設計分析及背景理解；未定案提案或個案不構成正式支援能力。 |
| T3 — 具佐證的第二手資料 | 有引用、版本與可重現方法的第三方文章或教學。 | 補充解釋及探索線索；重要主張須由適用 T1 證據或相關一手驗證交叉確認。 |
| T4 — 未驗證資訊 | 無來源主張、無佐證論壇回答、AI 生成摘要。 | 僅作搜尋或驗證起點，不能作為規格的唯一依據。 |

- 權威性、適用性與驗證狀態分開判斷。檢查版本、日期、設定、workload、部署模式，以及來源是在描述提案還是已發布行為。
- 官方身分不會使行銷說法或 benchmark 成為通用保證。原始碼觀察也不必然是正式支援的公開介面承諾。
- 不假定 `/latest/` 文件適用於任一 Doris 候選版本。版本相關主張須檢查對應版本資料；找不到時，標為未驗證並指出所需檢查。
- 重要技術主張附近保留引用 ID；來源紀錄包含標題、URL 或 repository 路徑、外部來源 tier、已知版本／revision 與發布日期、存取日期、支持的主張、適用條件及本地驗證狀態。未知者標為 `unknown` 或 `not verified`。
- 內部核准決策與使用者陳述屬於決策權威，不屬於外部來源分級；分別記錄出處，不直接標為 T1。
- 目前沒有來源白名單或黑名單。優先採用適用的一手證據，其他來源依表列用途使用。
- 來源不一致時保留衝突；若有依據，可說明版本或範圍差異。不以平均說法或默默選擇方便的來源來解決。
- 無法存取來源時須明說，不虛構引用、引文、驗證結果或存取日期。
- Apache Doris 的能力不自動等於本服務提供的能力或保證；須另行確認服務範圍及實作狀態。

## 5. 混合式文件生成流程

1. **檢視輸入。** 閱讀 repository 指引、相關既有文件與決策，確認讀者、文件類型、範圍及相依關係，保留使用者既有工作。
2. **先問重要問題。** 缺漏資訊若會明顯改變服務承諾、架構、存取邊界、資料語意或驗收條件，先釐清；相關問題集中詢問，不要求所有小細節都有答案才開始。
3. **其餘缺口先形成草稿。** 依已知資訊組織內容，明確標示提案、假設及待釐清問題。重要問題應交代需要的決策及影響。
4. **核對證據。** 依 tier 規則驗證重要外部主張，將產品需求追溯到使用者決策或已核准規格，區分上游能力與本服務提供內容。
5. **產出雙語配對。** 提供繁體中文敘述搭配英文技術術語，以及完整英文版本，檢查語意一致性。
6. **審閱與決策。** 向使用者摘要重要變更、未決事項、證據缺口及受影響文件。只有使用者可核准；完整草稿或翻譯本身不代表已核准。
7. **依指示定稿或發布。** 套用被接受的決策，同步相關文件及語言版本。沒有對應使用者決策時，不標示已核准／已發布，也不執行發布。

新主題先建立目的與服務邊界，再進入詳細設計。依目前任務需要建立文件，不自動產生表格中的所有類型。

## 6. 雙語與結構慣例

- 產品文件預設以同目錄的 `<topic>.zh-TW.md` 與 `<topic>.en.md` 配對。日後已有 repository 結構時予以沿用，不自行大量重新命名或翻譯無關舊文件。
- 兩種語言具有相同語意地位。先以討論使用的語言起草，再產出另一版本；有歧義時向使用者確認，不假定其中一種語言優先。
- 成對文件使用相同的穩定文件 ID 與 revision、等價狀態及互相連結。標題可以在地化；若使用需求、決策或引用 ID，兩種語言須一致。
- 需求、義務、數值、單位、範例、限制、證據狀態、引用與待釐清問題保持等價。準確翻譯 `must`、`should`、`may` 等規範強度，不因翻譯提高承諾。
- 中文採繁體中文敘述並保留英文技術術語。不熟悉的縮寫首次出現時說明，服務／元件名稱與識別碼保持一致。術語有歧義或重用需要時，維護共用 glossary。
- 最低文件 metadata：文件 ID、類型、讀者、生命週期狀態、revision 或最後更新日期、審閱者、適用服務／版本（含未決版本）及另一語言的連結。已知時才加入 owner，不虛構人物或日期。
- 建議生命週期：`Draft → In Review → Approved → Published`；僅在適用時使用發布階段，被替代文件使用 `Superseded`。這是輕量預設，不代表增加公司審核角色。
- 依文件責任選取適用章節，視需要附上決策、待釐清問題、參考來源及相關文件。避免空白模板章節，僅在有助理解時標示 `not applicable`。
- 雙語變更須在兩個版本一致後，才能視為可送核准。如果其中一版無法完成，回報雙語配對尚未完成，不宣稱同步完成。
- skill 本身是命名例外：OpenCode 要求入口名稱為 `SKILL.md`，中文對照檔為 `SKILL.zh-TW.md`。

## 7. 對外內容與 observability

- 對外文件描述對目標讀者已確認可用的能力與承諾。若使用者要求提前溝通，可將已核准但尚未開放的設計寫為明確標示的規劃或 preview 內容。
- 從已核准內部規格衍生使用者文件時，也須檢查開放狀態。申請與審核流程只描述已決定部分，不虛構審核者、處理時間或核准保證。
- 撰寫外部 monitoring／logging 文件時，釐清相關身分／存取範圍、可見資訊、遮蔽／不提供資訊、調查流程，以及已決定的保留／查詢限制。未決政策先保留為內部待釐清問題。
- 對外範例、截圖、圖表與 sample logs 必須符合已決定的可見性規則。不假定內部畫面可直接對外提供；規則尚未決定時，使用明確標示為示意的 placeholder。
- 區分 monitoring 畫面、log 調查、metrics 存取與 alerting 責任。未來使用者自行告警，不代表本服務負責告警傳送。
- 內部基礎設施細節與維運程序保留於其主要內部文件，除非已明確核准且使用者確實需要。外部參考資料不能決定內部資訊揭露政策。

## 8. 完成檢查

回報完成前確認：

- 讀者與文件類型明確，既有決策與使用者修改已保留。
- 現況、已決議設計、提案、假設與未知事項可區分。
- 重要外部主張有適當證據、適用性檢查及真實驗證狀態。
- 對外承諾符合已核准服務範圍與可用狀態，並遵守資訊揭露規則。
- 雙語版本、互相連結、ID、數值與規範強度一致。
- 共用事實變更（例如配額、保留期限、存取規則、功能範圍）已檢查相關 PRD、Feature Spec、架構／Data Flow、Service Spec 及手冊。在任務範圍內更新受影響文件，或明確列出待同步項目；仍有缺口時不宣稱全面一致。
- 使用適合文件變更的可用工具檢查連結與 Markdown 結構。
- 最後摘要指出異動檔案、重要決策、剩餘問題及實際審閱／驗證狀態。不宣稱尚未發生的人工核准、實作驗證或發布。
